# API Specification Management

## Purpose

API Specification Management provides the SDK interface for managing API
Specifications associated with Veracode DAST API Targets.

This module is responsible only for API Specification operations exposed
by the Target Configuration Service. It does not create, update, delete,
or otherwise manage Targets themselves.

Target Management remains the owner of Target lifecycle operations.
This module extends Target capabilities by allowing SDK consumers to
upload, retrieve, and download API Specifications for existing API
Targets.

---

## Scope

This module implements only the API Specification operations exposed by
the Target Configuration Service:

- Upload an API Specification.
- Retrieve API Specification metadata.
- Download the API Specification contents.

This module does **not** manage:

- Target creation.
- Target updates.
- Target deletion.
- Target linking.
- Scan execution.
- Scan configuration.
- Authentication management.
- Team management.

Those capabilities belong to their respective SDK modules.

---

## Dependencies

This specification depends on the following completed modules:

- Authentication
- Shared HTTP Client
- Target Management

API Specification Management requires an existing Target. The SDK never
creates a Target automatically as part of an API Specification operation.

---

## Relationship with Target Management

Target Management owns the Target resource.

API Specification Management operates on an already existing Target by
using its `target_id`.

Typical workflow:

```python
target = client.targets.get(target_id)

client.api_specifications.upload(
    target.target_id,
    "openapi.yaml"
)
```

The module never resolves Targets by name and never performs Target
creation.

---

## Public SDK API

The public SDK should read similarly to:

```python
client.api_specifications.upload(
    target_id,
    file_path
)

client.api_specifications.get(
    target_id
)

client.api_specifications.download(
    target_id,
    destination_path
)
```

The module exposes business operations rather than raw HTTP requests.

---

## Responsibilities

API Specification Management is responsible for:

- Uploading API Specification files.
- Retrieving API Specification metadata.
- Downloading API Specification contents.
- Validating SDK-level parameters.
- Translating API responses into SDK models.
- Raising meaningful business exceptions.

It is **not** responsible for:

- Creating Targets.
- Validating Target existence beyond API responses.
- Linking Applications.
- Managing Scans.

---

## Validation Responsibilities

The module performs only client-side validation that can be verified
without contacting the API.

Typical examples include:

- Required parameters.
- Empty strings.
- Invalid local file paths.
- Invalid destination paths.

Server-side validation performed by Veracode is never duplicated by the
SDK.

---

## Error Handling

The module follows the same error strategy used across the SDK.

### HTTP errors

HTTP errors returned by the shared HTTP Client propagate unchanged.

Examples include:

- Authentication failures.
- Authorization failures.
- Unknown Target.
- Invalid API Specification.
- Server errors.

### Business exceptions

Business exceptions are raised only for SDK-level validation failures,
such as:

- ApiSpecificationValidationError
- ApiSpecificationFileNotFoundError

The module never wraps HTTP exceptions generated by the shared HTTP
Client.

---

## Logging

HTTP request logging is handled by the shared HTTP Client.

API Specification Management logs only meaningful business events, such
as:

- Upload started.
- Upload completed.
- Metadata retrieval.
- Download started.
- Download completed.
- Business validation failures.

The module must never log:

- HTTP headers.
- Authentication information.
- File contents.
- API Specification contents.

---

## Models

Typical request models include:

- ApiSpecificationUploadRequest

Typical response models include:

- ApiSpecification

These models represent SDK objects rather than raw OpenAPI schemas.

---

## Out of Scope

This phase does not include:

- Editing API Specifications.
- Version history.
- API Specification comparison.
- API Specification validation beyond local checks.
- Automatic Target creation.
- Application linking.
- Scan execution.

Those capabilities belong to future specifications.

---

## OpenAPI Review

Before generating requirements, review the Target Configuration Service
OpenAPI and identify:

- Available API Specification endpoints.
- Request models.
- Response models.
- Multipart upload requirements.
- Download behavior.
- Validation rules.
- Error responses.
- HTTP status codes.

The generated specification must remain fully traceable to the OpenAPI.

---

## Expected Result

After this specification is implemented, SDK consumers should be be able
to manage API Specifications independently from Target lifecycle
operations.

Example:

```python
client = VeracodeClient()

client.api_specifications.upload(
    target_id,
    "openapi.yaml"
)

spec = client.api_specifications.get(target_id)

client.api_specifications.download(
    target_id,
    "downloaded-openapi.yaml"
)
```

This keeps API Specification Management focused on API Specification
operations while allowing Target Management to remain responsible for the
Target lifecycle.
